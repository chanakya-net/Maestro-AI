A guide to getting software built with Maestro-AI.

Maestro-AI helps coding agents turn a request into small tasks, build and check those tasks, and bring the results together in a pull request.

You decide what should be built. The skills guide the conversation and the work. A Python program keeps track of the agents, files, and results while the work runs.

The skills

Instructions your coding agent follows

Seven guides cover requirements, issue creation, coding, debugging, design discussions, and concise replies. Each guide has a specific job and a clear stopping point.

The runtime

The program that keeps work moving

The ai-skills command starts agents, schedules ready tasks, saves progress, checks results, and helps recover interrupted work. It runs on Windows, macOS, and Linux.

You bring a code repository and installed, authenticated coding agents. Maestro-AI coordinates those agents; their models and accounts still provide the AI.

The usual path: understand, plan, build

Start with the part you need. If your issues are already ready to implement, you can go straight to run-with-it.

  1. Make the request clearbreak-reqDiscuss behavior, constraints, and unanswered questions. Save the agreed requirements.
  2. Turn it into small taskscreate-git-issueReview a product requirements document (PRD), then approve the issue breakdown before it is published.
  3. Build and check the workrun-with-itWork through ready issues, run checks, handle review, and prepare a final pull request.

Keep decisions visible. Requirements discovery stops at its requirements file. Issue creation asks for approval before publishing the PRD and implementation issues. Execution then works from those prepared issues.

Invoke a skill through your coding agent's skill mechanism. These names are skills, not shell commands.

What happens when you ask for a feature?

This example follows a run using GitHub issues and a pull request. Imagine your request is:

“Let users export their invoices as a CSV file.”

  1. Agree on what “export” means

    break-req helps settle which fields belong in the file, who can export, and whether filters apply. It explores the existing code before asking you for facts it can find itself.

  2. Approve a plan made of small, complete behaviors

    create-git-issue might propose a basic export first, followed by support for active filters and an empty-results message. Each issue includes the necessary work across the app and its tests. You review the breakdown before publishing.

  3. Start only the work that is ready

    run-with-it reads the prepared issues. An issue waits until its prerequisites are complete. Independent work can run together; overlapping work is kept apart by the scheduling rules.

  4. Build and verify each issue in its own workspace

    An issue coordinator assigns coding and checking work to agents. Each issue has an isolated Git worktree: a separate working folder and branch. Workers implement the behavior, run the required checks, and commit their changes.

  5. Review, revise, and combine accepted changes

    When review is required, a reviewer can approve, request changes, or reject the work. Revisions are checked again. Accepted issue branches are merged into one shared feature branch; merge problems go through a separate recovery step.

  6. Report the outcome and prepare the final PR

    Successful issues receive a GitHub update and are closed as they finish. Failed or blocked issues stay open with an explanation. Once every issue has an outcome, the coordinating agent reports the results and prepares the final PR from the shared feature branch.

A final PR is the review point. Issue completion and integration into the shared feature branch happen during the run. The final PR proposes those changes to the base branch; creating it does not merge it.

Who does what behind the scenes?

The work is divided so one agent does not need to remember every detail of every issue.

Main orchestrator

Organizes the whole run

The agent in your main session prepares the issues, dependency plan, and context. It watches progress and prepares the final report and PR. It does not implement the issues itself.

Python pool

Keeps ready work moving

One scheduler starts issue coordinators, respects dependencies and concurrency limits, and fills a slot when it becomes free. It saves outcomes and carries out per-issue GitHub updates.

Issue coordinator

Owns one issue from start to finish

Called a “Sub-Coordinator” in the source. It arranges complexity scoring, model selection, planning when needed, implementation, review, and integration. It returns a compact result report.

Workers

Do one specific job

Workers score, plan, implement, review, or revise. Recovery workers handle missing result reports or failed merges. Each worker receives its scope, files, and required output.

The default is up to four issue coordinators at once, subject to readiness and ownership rules. That limit is for issues; coordinators also launch workers for their individual phases. Setting PARALLEL_JOBS=1 runs one issue at a time.

“Worktree” means a separate Git working folder. “Artifact” means a saved result file, such as a plan, review, or verification report. Both let the next agent pick up work from files instead of relying on chat memory.

How does it choose an agent and model?

Each issue is scored for difficulty. The router uses that difficulty and the worker's job to choose from eligible models, while balancing the configured usage targets. Planning is routed two difficulty levels higher and review one level higher, up to the highest level.

The choices live in the repository's configuration. This guide does not repeat a model list that can drift out of date.

Models and routing policy

assets/agent-registry.json defines model membership, difficulty levels, reasoning effort, and usage targets. The router records its selection reason.

How each agent is launched

assets/agent-definitions.json defines agent commands, aliases, permissions, and how prompts are passed to each CLI.

How the separate paired-design discussion works

For pair-colleague, you explicitly choose both colleagues' agent, model, and reasoning effort. Both see the same saved context for a round and work read-only. The coordinating agent reads both responses, records agreement and disagreement, and decides the next focus.

By default, the discussion runs for at least 3 rounds and at most 8. Matching “ready” responses do not end it automatically: the coordinating agent must judge whether there is enough evidence to decide. The output is a decision document, not an implementation.

How do you know what happened?

Saved state records which issues are waiting, running, completed, or blocked. Progress messages show the current stage and activity counts. A process exiting successfully is not enough to mark work complete: managed results must pass validation, including the required verification and Git evidence for implementation work.

If a session is interrupted

The runtime checks the saved process identities and results before starting replacement work. Existing agents can still be running after the chat or terminal stops. Live or uncertain ownership prevents a duplicate launch.

If something fails

Infrastructure failures, missing reports, failed tests, and rejected reviews have different recovery paths. Retries are bounded. Unverified work is preserved for recovery rather than treated as successful.

Only completed prerequisites release dependent issues. An empty worker pool can still leave blocked work behind. The final report needs to show both what finished and what could not proceed.

For GitHub intake, dependencies come from each issue's ## Blocked by section. A link to the parent PRD is context, not a task dependency. If GitHub access is unavailable, the skill permits a local issues.md fallback under its intake rules; GitHub comments, issue closure, and PR creation still require GitHub access.

Resume through the skill using the saved run. Keep the same pool configuration or pair run directory so the runtime can reconcile existing attempts. Do not reset running issues to pending just because a session ended.

Stopping and cleaning up a run

Use the runtime's stop operation before discarding work. It checks the processes owned by that run and confirms shutdown before cleanup can proceed. If ownership or shutdown cannot be confirmed, preserve the state for investigation.

Failed or interrupted runs retain state and worktrees. Destructive cleanup needs authorization; user-modified files are preserved. Active runs keep using their selected runtime version, even after a newer version is installed.

The exact commands and cleanup rules are in the run-with-it skill.

Get started

You need Python 3.12 or newer and Git. To execute work, install and authenticate the coding-agent CLIs you want to use. GitHub operations also need the authenticated gh CLI. Providers distributed through npm need Node.js.

The installer registers the skills and packages the runtime. It does not install Python or coding agents, or sign in to provider accounts for you.

1. Get the repository

git clone https://github.com/chanakya-net/Maestro-AI.git
cd Maestro-AI

2. Install the runtime and skills

Choose the instructions for your operating system. The dry run previews what the skill installer will change.

macOS / Linux 
python3.12 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/python -m ai_skills install --source . --dry-run
.venv/bin/python -m ai_skills install --source .

Use an installed Python 3.12 or newer if its command has a different name.

Windows 
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install .
.venv\Scripts\python.exe -m ai_skills install --source . --dry-run
.venv\Scripts\python.exe -m ai_skills install --source .

3. Check the setup

In that Python environment, run:

python -m ai_skills doctor --json
python -m ai_skills agent list --detected-only

Here, python means the environment's interpreter. Activate the environment or use its full path from step 2. The installed ai-skills command provides the same operations.

doctor checks the interpreter and packaged resources. The agent list shows detected tools; use each provider's own sign-in process to establish account access.

4. Open your coding agent in the project you want to work on

Invoke break-req for a new idea, help-me-debug for a diagnosis, or run-with-it for prepared issues. Let the skill prepare the files and runtime configuration; you do not need to assemble the scheduler's JSON by hand.

For model options, installation profiles, overrides, and command reference, use the README or python -m ai_skills --help.

The current runtime uses Python commands on all three operating systems. Old Bash and PowerShell launch recipes are historical. For exact behavior, follow the maintained skill files, runtime code, and README.

For contributors: run the checks

In a Python 3.12+ environment at the repository root:

python -m pip install -e ".[dev]"
python -m pytest -q
python -m build

The automated suite uses fixture providers and does not require paid model calls. Live provider sign-in and interactive registration need separate checks in the target environment.
